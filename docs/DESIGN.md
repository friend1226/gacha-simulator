# 가챠 시뮬레이터 설계문서 (Implementation Spec)

> **문서 목적**: 구현 에이전트(Codex)가 이 문서만 읽고 구현을 시작할 수 있도록 하는 것.
> 아키텍처 결정은 확정된 것으로 취급하고, 명시되지 않은 세부사항만 구현자가 재량으로 결정한다.
> **문서 버전**: 1.1

## 0. 개요

### 0.1 무엇을 만드는가

블루아카이브, 소녀전선2, 엔드필드 등의 **가챠(확률형 아이템) 시스템을 모델링하고 확률 통계를 산출하는 도구**.

사용자는 블록 기반 UI로 가챠 규칙(엔티티, 확률, 천장, 트리거)을 구성하고, 두 가지 엔진으로 통계를 얻는다.

- **몬테카를로(MC) 엔진** — 무작위 시뮬레이션 반복. 모든 모델에 적용 가능. 결과는 근사값 + 신뢰구간.
- **마르코프(DP) 엔진** — 상태 전이 확률의 정확한 전개. 마르코프 조건을 만족하는 모델에만 적용 가능. 결과는 정확값.

### 0.2 확정된 핵심 결정

| # | 결정 | 근거 |
|---|---|---|
| D1 | 수치 백엔드를 3계층으로 분리하고 **`ScaledF64`를 기본값**으로 한다 | f64는 1e-308 미만 언더플로. 이 DP는 뺄셈이 없어 유효숫자 손실은 없고 지수부만 문제이므로, 지수를 별도 i64로 들면 해결됨 |
| D2 | 정확 모드는 **유리수(Fraction)가 아니라 공통분모 BigInt**로 구현한다 | Fraction은 덧셈마다 GCD가 돌아 DP 내부 루프에서 병목. 레이어 공통 분모를 쓰면 정수 곱·합만 남음 |
| D3 | 엔티티는 **입력은 트리, 내부는 배타적 리프**로 관리한다. 카운트는 **리프에만 저장**하고 상위 엔티티 카운트는 파생값이다 | 포함관계 불변식이 구조적으로 보장되고, MC/DP가 동일 표현을 공유. 확정 지급 시 상위 카운트가 자동으로 함께 증가 |
| D4 | 사용자 표현식은 **빌트인 연산/함수만** 허용한다 (루프·부수효과·임의 이력 접근 없음) | 마르코프 성질 보존. 임의 코드를 허용하면 DP 엔진 자체가 불가능 |
| D5 | 코어는 **Rust**, UI는 **TypeScript + Blockly**. WASM(웹)과 Tauri(데스크톱) 양쪽 배포 | 단일 코어로 두 배포 형태를 모두 커버. BigInt 백엔드도 순수 Rust로 WASM 컴파일 가능 |

### 0.3 용어

| 용어 | 정의 |
|---|---|
| **시행(trial)** | 가챠 1회 뽑기 |
| **엔티티(entity)** | 사용자가 정의하는 당첨 대상. 트리 구조로 중첩 가능 |
| **리프(leaf)** | 컴파일 결과로 생성되는 **서로소인** 최종 결과. 매 시행은 정확히 1개의 리프를 산출 |
| **제어 카운터(control var)** | 전이 확률 계산에 사용되는 상태 변수. 상한 선언 필수 (예: 천장 카운터 0~89) |
| **자동 리프 카운터(stat)** | 엔진이 리프마다 자동 관리하는 카운터. 사용자가 선언하지 않는다 |
| **집계 변수(accumulator)** | 확률에는 영향을 주지 않고 경로 의존 통계를 누적하는 사용자 선언 변수. 상한 필수 |
| **레이어(layer)** | DP에서 특정 시행 횟수 n에 대응하는 상태-확률 분포 전체 |

## 2. 수치 백엔드 (`numeric`)

### 2.1 `Prob` trait

```rust
pub trait Prob: Clone + Send + Sync + 'static {
    /// 0
    fn zero() -> Self;
    /// 1
    fn one() -> Self;
    /// 정확한 유리수로부터 생성 (분자, 분모)
    fn from_ratio(num: &BigInt, den: &BigInt) -> Self;

    fn add_assign(&mut self, other: &Self);
    fn mul(&self, other: &Self) -> Self;

    fn is_zero(&self) -> bool;
    /// 표시용. 정보 손실 가능
    fn to_f64_lossy(&self) -> f64;
    /// 표시용 문자열. 유효숫자 지정
    fn to_decimal_string(&self, sig_digits: usize) -> String;
    /// 프루닝 판정용. 이 백엔드가 프루닝을 지원하지 않으면 None
    fn magnitude_log10(&self) -> Option<f64>;
}
```

**중요**: DP/MC 엔진은 이 trait에 대해 제네릭하게 작성한다. 백엔드별로 엔진을 복제하지 않는다.

### 2.2 계층별 구현

#### (a) `F64` — 최대 속도

f64 그대로. 1e-308 미만은 0으로 flush. `magnitude_log10` 지원 → 프루닝 가능.

**용도**: 파라미터 탐색, 실시간 프리뷰, 대규모 N.

#### (b) `ScaledF64` — 기본값

```rust
pub struct ScaledF64 {
    mantissa: f64,   // 불변식: 0.0 이거나 [1.0, 2.0) 범위
    exponent: i64,   // 실제 값 = mantissa * 2^exponent
}
```

**구현 요구사항**:

- `mul`: 가수는 곱하고 지수는 더한 뒤 정규화. `frexp`/`ldexp` 상당 연산 사용
- `add_assign`: 지수 차이가 60 이상이면 큰 쪽을 그대로 반환(작은 쪽은 유효숫자에 영향 없음). 아니면 지수를 맞추고 더한 뒤 정규화
- 정규화는 비트 조작(`f64::to_bits`)으로 구현. `frexp` 라이브러리 호출보다 3~5배 빠름
- 오버플로/언더플로는 i64 지수 범위 내에서 사실상 발생하지 않음. 발생 시 명시적 에러

**정밀도 보장**: 이 DP는 음이 아닌 값의 곱과 합만 수행하므로 자릿수 소거가 없다. 누적 상대오차는 대략 `N × (리프 수 + 1) × 2^-53`. N = 10,000, 리프 4개일 때 약 `5.5e-12` → **유효숫자 11자리 이상 보장**.

이 성질은 테스트로 검증해야 한다 (§9.3).

#### (c) `ExactInt` — 정확 모드

**핵심 설계**: 셀마다 유리수를 들지 않는다. **분모는 레이어 전체가 공유하는 스칼라 하나**이고, 셀에는 BigInt 분자만 저장한다.

```rust
/// 레이어 단위로 관리되는 분모. 셀에는 저장되지 않음.
pub struct ExactLayer {
    denominator: BigInt,              // 이 레이어의 공통 분모
    cells: HashMap<StateId, BigInt>,  // 분자만
}
```

**전개 알고리즘**:

1. 컴파일 시, 모델의 **도달 가능한 모든 확률값**을 유리수로 열거한다. 제어 상태 공간이 유한하고 표현식이 순수하므로 항상 가능하다.
2. 그 분모들의 최소공배수 `L`을 계산한다.
   - 예: 확률이 {7/1000, 23/1000, 970/1000} → L = 1000
   - 예: 상대확률 7/30이 섞이면 → L = lcm(1000, 30) = 3000
3. 각 확률 `a/b`를 `(a · L/b) / L` 형태의 정수 분자 `a' = a·L/b`로 미리 변환한다.
4. 레이어 전개:
   ```
   next.denominator = cur.denominator * L
   next.cells[s'] += cur.cells[s] * a'[leaf]      // 정수 곱셈 + 덧셈만
   ```
5. **GCD는 내부 루프에서 절대 호출하지 않는다.** 선택적으로 레이어 완성 후 1회, 전체 분자와 분모의 gcd로 약분한다 (`--exact-reduce` 옵션, 기본 off).

**L이 폭발하는 경우**: 사용자 표현식의 나눗셈이 큰 소수 분모를 만들면 L이 커진다. 컴파일 시 `L`의 비트 수를 계산해 임계값(기본 64비트) 초과 시 경고하고, 128비트 초과 시 정확 모드를 거부한다.

**메모리 추정식** (UI에 노출):
```
셀당 바이트 ≈ n · log2(L) / 8
레이어 총량 ≈ 셀 수 × 셀당 바이트
```
예: N=1000, L=1000(≈10비트), 셀 500,000개 → 셀당 1.25KB → **625MB/레이어**.
따라서 정확 모드는 하드 리밋이 필수다 (§2.3).

**프루닝 금지**: 정확 모드에서는 프루닝을 사용하지 않는다. `magnitude_log10`은 `None`을 반환하고, 엔진은 이를 보고 프루닝 경로를 비활성화한다.

### 2.3 정확 모드 가드레일

정확 모드 실행 전 다음을 검사하고, 초과 시 실행을 거부하며 예상치를 보여준다.

| 항목 | 기본 한계 | 설정 가능 |
|---|---|---|
| 최대 시행 횟수 N | 2,000 | 예 |
| 레이어당 최대 상태 수 | 200,000 | 예 |
| 예상 피크 메모리 | 2 GB | 예 |
| L 비트 수 | 64 (경고) / 128 (거부) | 아니오 |

또한 정확 모드 실행은 반드시 **취소 가능**하고 **진행률을 보고**해야 한다 (레이어 단위 콜백).

### 2.4 백엔드 선택 UX

| 사용자 표기 | 내부 | 설명 |
|---|---|---|
| 표준 (권장) | `ScaledF64` | 유효숫자 11자리 이상. 아무리 작은 확률도 표현 가능 |
| 고속 | `F64` | 1e-308 미만은 0으로 표시됨 |
| 정확 | `ExactInt` | 오차 0. 느리고 메모리 사용량이 큼 |

기본은 **표준**. UI에서 "고속"과 "정확"은 접힌 고급 설정에 둔다.

## 3. Model IR

블록 UI와 엔진 사이의 유일한 계약. **UI가 JS 코드 문자열을 생성해서는 안 된다.** 반드시 이 JSON을 생성한다.

### 3.1 스키마

```jsonc
{
  "irVersion": 2,
  "name": "블루아카이브 픽업 모집",

  // ── 엔티티 트리 (사용자 입력 형태) ─────────────────────
  "entities": [
    {
      "id": "star3",
      "name": "3성",
      "prob": { "lit": "0.03" },        // 십진 문자열 → 정확한 유리수로 파싱
      "children": [
        { "id": "pickup", "name": "픽업", "prob": { "lit": "0.007" } }
      ]
    }
  ],

  // 자식 확률 합이 부모를 넘을 때의 정책
  "nestingPolicy": "clampChildren",     // clampChildren | expandParent | scaleSiblings | error

  // ── 상태 변수 (사용자 선언) ───────────────────────────
  // stat 리프 카운터는 선언하지 않는다. 리프마다 자동 생성된다 (§3.5)
  "stateVars": [
    { "id": "pity",      "init": 0, "max": 89, "role": "control" },
    { "id": "guarantee", "init": 0, "max": 1,  "role": "control" },
    {
      "id": "spent", "name": "소모 재화", "init": 0, "max": 120000,
      "role": "accumulator",
      "update": [
        // 제어 변수나 trial을 참조하지 않아 사전계산 축은 (리프 × 현재값)만 사용한다.
        { "when": { "leafOf": "star3" },
          "set": { "add": [{ "var": "spent" }, { "lit": "120" }] } },
        { "when": { "not": { "leafOf": "star3" } },
          "set": { "add": [{ "var": "spent" }, { "lit": "120" }] } }
      ],
      "clampPolicy": "saturate"
    }
  ],

  // ── 확률 규칙: 엔티티 확률을 상태의 함수로 오버라이드 ────
  "probRules": [
    {
      "target": "star3",
      "expr": {
        "if":   { "ge": [{ "var": "pity" }, { "lit": "65" }] },
        "then": { "add": [{ "lit": "0.03" },
                          { "mul": [{ "lit": "0.03" },
                                    { "sub": [{ "var": "pity" }, { "lit": "65" }] }] }] },
        "else": { "lit": "0.03" }
      }
    }
  ],

  // ── 전이 규칙: 어떤 리프/조건에서 상태를 어떻게 갱신하나 ──
  // 제어 변수만 갱신한다. 리프 카운트 증가는 엔진이 자동 수행하므로
  // 여기에 count 증가를 적지 않는다 (적으면 이중 계산 버그).
  "transitions": [
    { "when": { "leafOf": "star3" }, "set": { "pity": { "lit": "0" } } },
    { "when": { "not": { "leafOf": "star3" } },
      "set": { "pity": { "add": [{ "var": "pity" }, { "lit": "1" }] } } }
  ],

  // ── 트리거 ───────────────────────────────────────────
  // "200회 도달 시 픽업 +1" = 확정 지급. grant 액션을 쓴다.
  "triggers": [
    {
      "at": { "trialCount": 200 },
      "grant": {
        "leaf": "pickup",          // 반드시 리프. 내부 노드 지정은 컴파일 에러
        "amount": 1,
        "consumesTrial": false,    // 지급이 시행 횟수를 소모하는가
        "appliesTransitions": true // 일반 당첨처럼 transitions를 적용하는가(천장 리셋 등)
      }
    },
    { "at": { "trialCount": 200 }, "set": { "guarantee": { "lit": "1" } } }
  ],

  // ── 실행 설정 ────────────────────────────────────────
  "run": {
    "maxTrials": 1000,
    // 리프/엔티티/집계 변수. 엔티티명은 하위 리프 전체로 확장된다
    "trackJoint": ["pickup", "spent"],
    "numeric": "scaled",                    // f64 | scaled | exact
    "trialSeries": "marginal",              // none | marginal | checkpoints
    "seriesCheckpoints": [10, 50, 100, 1000]
  }
}
```

`irVersion: 1`은 하위 호환으로 계속 읽되 accumulator와 시행 시리즈가 없는 모델로
해석한다. 새 프리셋과 UI 출력은 v2를 사용한다. `checkpoints`는 최대 20개이며 각 값은
`1..=maxTrials` 범위여야 한다.

### 3.2 리터럴 파싱 규칙 (중요)

`{ "lit": "0.007" }`은 **반드시 십진 문자열 → 유리수(7/1000)** 로 파싱한다.
f64로 먼저 파싱한 뒤 유리수로 변환하면 `0.007`이 `7.000000000000000145...`가 되어 정확 모드가 무의미해진다.

파싱 규칙:
- `"0.007"` → 7/1000
- `"1/3"` → 1/3 (분수 리터럴 허용)
- `"3e-5"` → 3/100000
- f64 리터럴 문법은 **허용하지 않는다**

### 3.3 표현식 언어

#### ℚ-safe 빌트인 (정확 모드에서 사용 가능)

| 분류 | 연산 |
|---|---|
| 산술 | `add` `sub` `mul` `div` `neg` `abs` |
| 정수 | `floor` `ceil` `round` `min` `max` `clamp` |
| 거듭제곱 | `pow` (지수는 **정수 리터럴만**) |
| 비교 | `eq` `ne` `lt` `le` `gt` `ge` |
| 논리 | `and` `or` `not` `xor` |
| 분기 | `if/then/else` |
| 참조 | `var`(상태 변수) `trial`(현재 시행 인덱스) `lit` |

#### ℚ-unsafe 빌트인 (사용 시 정확 모드 비활성화)

`sqrt` `ln` `exp` `pow`(비정수 지수) `sin` `cos`

이런 함수를 하나라도 쓰면 컴파일 결과에 `exactAvailable: false`가 설정되고, UI는 정확 모드 선택지를 비활성화하며 이유를 표시한다.

#### 금지 (파서가 거부)

루프, 재귀, 배열/이력 접근, 난수 호출, 외부 I/O, 부수효과가 있는 함수, 사용자 정의 함수 선언.

### 3.4 검증 규칙

컴파일 전 다음을 검사하고, 실패 시 **블록 ID를 포함한** 에러를 반환한다 (UI에서 해당 블록 하이라이트).

| ID | 검사 | 심각도 |
|---|---|---|
| E001 | 엔티티 id 중복 | error |
| E002 | 확률 표현식이 음수를 산출 가능 (정적 분석 가능한 경우) | error |
| E003 | 확률표 계산 런타임 실패 — 음수 확률(E002가 정적으로 못 잡은 경우의 백스톱), 최상위 리프 확률 합 > 1, 리프 확률 질량 불일치 중 하나 (`compile.rs`의 `calculate_leaf_probs`/`split_entity`) | error |
| E004 | `role: control`/`accumulator` 변수의 `max` 누락, 초기값 범위 오류, 또는 `clampPolicy: error`에서 범위 초과 가능 | error |
| E005 | `probRule`이 정의되지 않은 엔티티를 대상으로 함 | error |
| E006 | 표현식에 금지 연산 사용 | error |
| W001 | 자식 확률 합 > 부모 확률 (정적 감지 가능한 경우) | warning + 정책 적용 |
| W002 | 최상위 리프 확률 합 < 1 → "그외" 리프 자동 생성 | info |
| W003 | 조건이 논리적으로 만족 불가능 (예: `nPickup > nStar3`) | warning |
| W004 | 상태 공간이 DP 한계 초과 → MC 전용 | warning |
| W007 | `consumesTrial` 지급이 남은 논리 시행 예산을 초과해 적용되지 않음 | warning |
| E007 | `grant.leaf`가 내부 노드를 가리킴 (어느 리프인지 모호) | error |
| E008 | `transitions`/`triggers`가 리프 카운트를 직접 조작 | error |
| E009 | 자동 리프 카운터용 `role: stat`을 사용자가 선언 | error |
| W008 | accumulator가 자동 리프 카운터와 동일하여 파생 표시식으로 강등 | warning |
| W009 | accumulator 사전계산 테이블이 500,000 엔트리 이상 | warning |
| E010 | accumulator 사전계산 테이블 합계가 10,000,000 엔트리 초과 | error |

### 3.5 카운트 모델 (필독)

**저장되는 카운트는 리프 카운트뿐이다.** 엔티티 카운트는 파생값이며 상태에 저장하지 않는다.

```
저장:  count(pickup), count(star3__self), count(__other__)
파생:  nStar3 = count(pickup) + count(star3__self)
```

이 규칙에서 다음이 자동으로 따라온다.

1. **포함관계 불변식이 구조적으로 보장된다.** `nPickup ≤ nStar3`는 정의상 항상 참이며 런타임 검사가 필요 없다.
2. **확정 지급이 상위 카운트에 자동 전파된다.** "200회 도달 시 픽업 +1"은 `count(pickup) += 1` 하나만 수행하면 되고, `nStar3`는 파생식에 의해 저절로 +1 된다. **`nStar3`를 따로 증가시키면 이중 계산이 되므로 금지한다** (E008).
3. **DP 차원이 최소가 된다.** 리프 수를 L이라 하면 자유 차원은 `L-1`개다 (총합이 시행 횟수로 고정되므로 마지막 리프는 종속). 엔티티마다 차원을 두면 중복이다.

`count(__other__)`는 다른 리프 카운트와 시행 횟수로부터 결정되므로 상태에 저장하지 않는다.

**조건식과 결과 뷰에서는 엔티티 이름을 그대로 쓸 수 있다.** 컴파일러가 `nStar3` → `count(pickup) + count(star3__self)`로 전개한다. 사용자는 리프 개념을 몰라도 된다.

### 3.6 집계 변수(accumulator) 의미론

집계 변수는 확률식에서 참조할 수 없고 결과 통계에만 사용한다. 경로 의존 값은
`StateCodec`의 `control`/리프 카운트와 분리된 세 번째 구획에 저장한다. 갱신식은
엔진 루프에서 평가하지 않고 컴파일 시
`(집계 변수, 제어 상태, 시행, 리프, 현재값) → 다음값` 테이블로 만든다. 제어 상태나
시행에 의존하지 않는 축은 해당 테이블 차원을 1로 접는다.

자동 리프 카운터와 동일한 `x = x + 1 when leafOf(...)` 집계 변수는 `W008`을 내고
상태 축을 만들지 않은 채 리프 합으로 파생한다. `max` 초과 시 기본 `saturate`는
보정 횟수를 `accumulatorClampEvents`로 별도 보고하며, `error`는 컴파일을 거부한다.

사전계산 테이블은 전개 전에 모든 accumulator의
`제어상태 × 시행 × 리프 × (max+1)` 엔트리를 합산한다. 500,000 이상은 `W009`로
축별 크기와 완화 방법을 알리고, 기존 확률표 상한과 같은 10,000,000을 넘으면
OOM 위험 때문에 `E010`으로 컴파일을 거부한다. 여러 accumulator의 합계에도 같은
상한을 적용한다.

갱신 순서는 **일반 뽑기 확정 → transitions → accumulator 갱신 → grant**로 고정한다.
`appliesTransitions: true` 지급은 transition 뒤 accumulator 갱신도 일반 결과와 같이
적용한다.

### 3.7 지급(grant) 의미론

확정 지급은 게임마다 세부가 다르므로 명시적 필드로 제어한다.

| 필드 | 의미 | 기본값 |
|---|---|---|
| `leaf` | 지급 대상 리프 | 필수 |
| `amount` | 지급 개수 | 1 |
| `consumesTrial` | true면 지급이 시행 1회를 소모(전체 시행 횟수에 산입) | false |
| `appliesTransitions` | true면 해당 리프가 정상 당첨된 것처럼 `transitions`를 적용 (예: 천장 카운터 리셋) | true |

지급은 **해당 시행의 일반 뽑기·transition·accumulator 갱신이 끝난 직후**에 적용된다. 순서가 뒤바뀌면 천장 카운터 값이 달라지므로 이 순서를 고정한다.

`consumesTrial: true`인 지급은 일반 뽑기 직후 다음 논리 시행 슬롯 1개를 차지한다. `maxTrials`는 일반 뽑기와 이 슬롯을 합친 총 시행 예산이다. 따라서 지급 슬롯만큼 다음 일반 뽑기 번호를 건너뛰며, 남은 슬롯이 없으면 해당 지급은 적용하지 않는다. 지급의 전이와 조건 판정에는 지급이 차지한 논리 시행 번호를 사용한다. `amount`와 관계없이 지급 동작 하나가 슬롯 하나를 소모한다.

MC와 DP는 반드시 동일한 순서·의미론을 구현해야 하며, §9.1 교차 검증이 이를 잡아낸다.

## 4. 컴파일 파이프라인 (`compile`)

```
Model IR
  │
  ├─ 1. 검증 (§3.4)
  ├─ 2. 표현식 → 스택 바이트코드
  ├─ 3. 제어 상태 공간 열거
  ├─ 4. 확률 테이블 사전계산 (exact rational)
  ├─ 5. 리프 분할
  ├─ 6. 마르코프 판정 + 상태 공간 추정
  └─→ CompiledModel
```

### 4.1 표현식 → 바이트코드

AST를 재귀 순회하지 말고 스택 머신 바이트코드로 컴파일한다. 확률 테이블 계산이 `|control states| × N`번 실행되므로 인터프리터 오버헤드가 유의미하다.

```rust
enum Op {
    PushLit(Rational),
    PushVar(VarId),
    PushTrial,
    Add, Sub, Mul, Div, Neg, Abs,
    Min, Max, Floor, Ceil, PowInt(i32),
    Eq, Lt, Le, Gt, Ge,
    And, Or, Not, Xor,
    JumpIfFalse(usize), Jump(usize),
}
```

### 4.2 제어 상태 공간 열거

```rust
control_space_size = Π (max_i + 1)   for all control vars
```

예: `pity`(0~89) × `guarantee`(0~1) = 180.

이 값이 임계값(기본 10^7)을 넘으면 확률 테이블을 사전계산하지 않고 lazy 평가 + 캐시로 전환한다.

### 4.3 확률 테이블 사전계산 (핵심 최적화)

**확률 표현식은 항상 정확한 유리수로 한 번만 평가하고, 이후 엔진은 테이블만 읽는다.**

```rust
pub struct ProbTable {
    /// [control_state_index][trial_index_or_0] -> 리프별 확률
    /// trial에 의존하지 않으면 두 번째 차원은 크기 1
    entries: Vec<Vec<LeafProbs>>,
    trial_dependent: bool,
}

pub struct LeafProbs {
    exact: Vec<Rational>,   // 정확 모드용
    // 백엔드로 변환된 값은 엔진 초기화 시 1회 캐스팅
}
```

이 설계의 이점:
- 표현식 평가가 DP/MC 내부 루프에서 완전히 사라진다
- 정확 모드와 부동소수점 모드가 **동일한 확률값**을 사용함이 보장된다
- `ExactInt`의 L 계산이 이 테이블 위에서 자연스럽게 이루어진다

### 4.4 리프 분할

각 제어 상태에 대해 다음을 수행한다.

1. 트리를 후위 순회하며 각 노드의 확률을 확률 테이블에서 얻는다
2. `nestingPolicy`에 따라 부모-자식 **확률** 충돌을 해소한다.
   충돌은 `probRules`가 부모와 자식의 확률을 독립적으로 바꿔 자식 합이 부모를 넘길 때만 발생한다.
   **카운트 지급(`grant`)은 이 충돌과 무관하다** — 리프 카운트만 건드리므로 확률 구조를 바꾸지 않는다.

| 정책 | 동작 |
|---|---|
| `clampChildren` (기본) | 자식 합이 부모를 넘으면 자식들을 비례 축소해 부모에 맞춤 |
| `expandParent` | 부모 확률을 자식 합까지 확대 (상위 노드로 전파) |
| `scaleSiblings` | 같은 레벨 형제들을 비례 조정해 총합 유지 |
| `error` | 런타임 에러로 중단 |

3. 리프 확률을 산출:
   - 내부 노드 X의 "X 전용" 리프 = `P(X) - Σ P(자식)`
   - 잎 노드는 그대로 리프
   - 최상위 잔여분 = `1 - Σ P(최상위 노드)` → `__other__` 리프
4. 충돌 해소가 발생한 횟수를 카운트해 결과 메타데이터에 포함한다 (사용자가 모르고 지나가면 안 됨)

**출력 예시** (블아 기본 케이스):

| 리프 | 확률 |
|---|---|
| `pickup` | 7/1000 |
| `star3__self` | 23/1000 |
| `__other__` | 970/1000 |

상위 노드는 확률도 카운트도 저장하지 않고 리프 합으로 파생한다 (§3.5).

### 4.5 마르코프 판정

```rust
pub struct MarkovAnalysis {
    pub dp_available: bool,
    pub blockers: Vec<Blocker>,       // 왜 불가능한지
    pub control_states: u64,
    pub stat_states: u64,             // trackJoint 기준
    pub total_states: u64,
    pub est_bytes_per_layer: u64,
    pub est_runtime_ms: u64,
}
```

`dp_available = false`가 되는 조건:
- 상한이 선언되지 않은 control 변수 존재
- 상태 공간 추정치가 한계 초과
- (향후) 마르코프 성질을 깨는 기능 사용

**집계 축소**: 엔티티 카운터와 자동 리프 카운터로 복원 가능한 accumulator는 상태
축으로 만들지 않는다. 경로 의존 accumulator는 추적 여부와 관계없이 다음 갱신에
필요하므로 상태에 남는다. UI는 `(max+1)`배 상태 증가를 계산 규모에 즉시 반영한다.

## 5. 몬테카를로 엔진 (`engine_mc`)

### 5.1 기본 루프

```
for run in 0..R:
    state ← 초기 상태
    for trial in 1..=N:
        leaf ← sample(alias_table[control_index(state)][trial])
        state ← apply_transitions(state, leaf)
        state ← apply_triggers(state, trial)
        if mode == FirstHit && condition(state) && !hit:
            record_hit(trial); hit ← true; break
    if mode == Distribution:
        histogram[key(state)] += 1
```

### 5.2 요구사항

- **RNG**: `xoshiro256++` 또는 PCG64. **시드를 반드시 입력받고 결과 메타데이터에 기록**한다. `rand::thread_rng` 금지 (재현 불가)
- **병렬**: 스레드별로 RNG jump 함수로 분리된 스트림 사용. 각자 로컬 히스토그램을 만들고 마지막에 머지. 웹에서는 Web Worker + `SharedArrayBuffer` 또는 워커별 결과 전송
- **샘플링**: 제어 상태별로 alias table을 사전 구축 (O(1) 샘플링). 확률은 f64로 캐스팅해 사용 — 샘플링 오차는 MC 통계 오차에 비해 무시 가능
- **저장**: 개별 run의 이력을 저장하지 않는다. 히스토그램만 유지
- **진행률/취소**: 배치(예: 10,000 run)마다 콜백

### 5.3 출력

```rust
pub struct McResult {
    pub runs: u64,
    pub seed: u64,
    pub joint: HashMap<StatKey, u64>,      // 결합 히스토그램
    pub elapsed_ms: u64,
    pub clamp_events: u64,                 // §4.4 충돌 해소 발생 횟수
    pub accumulator_clamp_events: u64,
    pub trial_series: TrialSeries,
}
```

### 5.4 신뢰구간 (필수)

MC 결과의 모든 확률 셀에 **Wilson score 구간**(95% 기본)을 함께 산출해 표시한다. 이게 없으면 사용자가 근사값을 정확값으로 오해한다.

```
표시 예: 0.03412 ± 0.00058 (95% CI, R=1,000,000)
```

**자동 정지 옵션**: "관심 셀의 CI 폭이 X 이하가 될 때까지 실행" 모드를 제공한다.

## 6. 마르코프 엔진 (`engine_dp`)

### 6.1 상태 인코딩

```
state = (control vars..., accumulator vars..., tracked leaf counts..., absorbed_flag)
```

집계 차원은 **리프 카운트**다 (§3.5). 엔티티 단위 차원을 두지 않는다.
`trackJoint`에 엔티티명이 오면 컴파일러가 하위 리프 집합으로 전개하고,
전개된 리프 중 하나는 종속이므로 `L-1`개만 상태에 포함한다.
accumulator는 확률표 제어 인덱스와 분리되어 `control_invariant` 정규화 시에도 값이
보존된다.

혼합 진법 정수로 패킹한다:

```rust
index = c0 + m0*(c1 + m1*(c2 + m2*(...)))
```

### 6.2 레이어 표현

**희소 저장을 사용한다.** N=1000일 때 이론상 상태는 수십만 개지만 유효 질량은 수천 개 셀에 몰린다.

```rust
pub struct Layer<P: Prob> {
    cells: HashMap<u64, P>,       // 또는 정렬된 Vec<(u64, P)>
    pruned_mass: f64,             // 프루닝으로 버린 누적 질량
}
```

`FxHashMap` 또는 정렬 벡터 + 이진 탐색 중 벤치마크로 선택한다. 셀 수가 10^5 이하면 정렬 벡터가 캐시 지역성 면에서 유리할 가능성이 높다.

### 6.3 전개

```rust
for trial in 1..=N {
    let mut next = Layer::new();
    for (&state, prob) in layer.cells.iter() {
        if prob.is_zero() { continue; }
        let ctrl = control_index(state);
        let probs = &prob_table[ctrl][trial_index(trial)];
        for (leaf_id, p_leaf) in probs.iter().enumerate() {
            if p_leaf.is_zero() { continue; }
            let next_state = transition(state, leaf_id, trial);
            next.add(next_state, prob.mul(p_leaf));
        }
    }
    apply_pruning(&mut next);       // exact 모드에서는 no-op
    layer = next;
    snapshot_policy.on_layer(trial, &layer);
    progress_callback(trial, N);
}
```

### 6.4 프루닝

`ScaledF64`/`F64`에서만 활성화. 임계값 기본 `1e-18` (상대).

- 버린 질량을 `pruned_mass`에 누적
- 결과 메타데이터에 총 손실량 보고. 손실이 `1e-12`를 넘으면 UI에 경고
- 정확 모드에서는 `Prob::magnitude_log10()`이 `None`이므로 자동 비활성화

### 6.5 질량 보존 단언

매 레이어마다 `Σ cells + pruned_mass ≈ 1.0`을 검사한다.
- 부동소수점 모드: 허용 오차 `1e-9`
- 정확 모드: `Σ numerators == denominator` **정확히** 일치해야 함. 불일치는 버그이므로 panic

### 6.6 성능 목표

| 시나리오 | 백엔드 | 목표 |
|---|---|---|
| N=1,000, 리프 3개, 제어 180상태, 픽업만 추적 | ScaledF64 | < 300ms |
| N=1,000, 동일, 결합 추적 (nStar3 × nPickup) | ScaledF64 | < 8s |

### 6.7 시행별 결과 시리즈

`run.trialSeries`의 기본은 `marginal`이다.

| 모드 | 반환 내용 |
|---|---|
| `none` | 마지막 결합 분포만 반환 |
| `marginal` | 도달한 각 `(trial, 값)`에서 추적 축별 주변분포 반환 |
| `checkpoints` | 최대 20개의 지정 시행에서 완전 결합분포 반환 |

`consumesTrial` 때문에 시행 번호가 건너뛸 수 있으므로 배열 인덱스가 아니라 명시적인
`trial` 값을 사용한다. exact는 레이어 저장 시 공통분모에서 f64로 한 번만 변환하고,
MC 주변분포의 모든 셀은 반복 수와 Wilson 95% 구간을 포함한다.
| N=200, 동일, 픽업만 추적 | ExactInt | < 30s |

## 7. 조건 시스템 (`condition`)

### 7.1 조건 표현

조건은 카운트에 대한 **불리언 표현식**이다. AND/OR/XOR/NOT과 비교 연산을 지원한다.

조건식에서는 **엔티티 이름을 그대로 쓴다.** 컴파일러가 리프 합으로 전개한다 (§3.5).
아래 예의 `nStar3`는 `count(pickup) + count(star3__self)`로 치환된다.

```jsonc
{
  "condition": {
    "or": [
      { "ge": [{ "var": "nPickup" }, { "lit": "2" }] },
      { "and": [ { "ge": [{ "var": "nStar3" }, { "lit": "6" }] },
                 { "eq": [{ "var": "nPickup" }, { "lit": "0" }] } ] }
    ]
  },
  "maxTrials": 300
}
```

**XOR은 비단조적**이므로 복잡한 DFA를 만들지 않는다. 대신:
- 매 시행 후 조건을 평가한다
- 처음 참이 되는 순간 **흡수 비트를 세팅**하고 그 시행 번호를 기록한다
- 흡수된 상태는 이후 전이하지 않는다

이 방식으로 MC와 DP가 완전히 동일한 의미론을 갖는다.

### 7.2 출력

```rust
pub struct FirstHitResult {
    pub pmf: Vec<Probability>,      // pmf[k] = 정확히 k회에 처음 달성
    pub cdf: Vec<Probability>,
    pub failure_reachable: Probability,   // maxTrials 내 미달성
    pub failure_impossible: bool,         // 정적 분석 결과 달성 불가
    pub mean: Option<f64>,                // 실패 확률>0이면 조건부 평균으로 보고
    pub percentiles: Vec<(f64, u32)>,     // 50%, 75%, 90%, 95%, 99%
}
```

ExactInt 백엔드는 동일한 필드를 `ExactFirstHitResult`로 반환한다. `pmf`, `cdf`, `failureReachable`의 각 값은 최종 레이어 공통분모와 BigInt 분자 문자열을 포함하며, 표시용 `f64`가 언더플로해도 정확값은 보존된다. 흡수된 질량은 활성 셀과 함께 레이어 약분·질량 보존 검사에 포함한다.

### 7.3 정적 만족가능성 검사 (W003)

시뮬레이션을 10분 돌린 뒤 "0%"를 보는 것을 방지한다. 컴파일 시 다음을 검사한다:

- 포함관계 위반: `nPickup > nStar3` 형태. 리프 전개 후 `count(pickup) > count(pickup) + count(star3__self)`가 되어 `count(star3__self) < 0`을 요구하므로 정적으로 검출된다
- 범위 위반: `nStar3 > maxTrials`
- 리프 확률이 항상 0인 엔티티에 대한 양수 조건

검출 시 실행 전에 경고한다.

## 8. 스냅샷 (`snapshot`)

### 8.1 정책

문서 원안의 "1~N 전 레이어 저장"은 N=1000, f64 기준 4GB이므로 채택하지 않는다. 대신 3단계 정책을 제공한다.

| 정책 | 저장 내용 | 용량 (N=1000, 결합추적) |
|---|---|---|
| `aggregate` (기본) | 매 레이어의 **주변분포 + 요약통계만** | ~5 MB |
| `checkpoint` | 로그 간격(1,2,5,10,20,50,100,200,500,1000) + 사용자 핀 레이어의 **전체 결합분포** | ~50 MB |
| `full` | 매 레이어 전체 결합분포 | ~4 GB (경고 후에만 허용) |

**핵심**: 전체를 저장하는 대신 **재계산**한다. 체크포인트가 로그 간격이면 임의 시행 K의 정확한 분포를 최대 K/2 스텝 재계산으로 복원할 수 있다. 일반적으로 100ms 이내.

### 8.2 포맷

```
[Header]
  magic: "GCHS", version: u16
  numeric_backend: u8
  model_hash: [u8; 32]     // IR의 canonical JSON을 SHA-256
  n_trials: u32, layer_index: u32
  state_dims: Vec<(var_id, max)>
  cell_count: u64
[Body]  zstd 압축
  ExactInt 모드: denominator (varint 길이 + 바이트열)
  cells: (state_index: varint delta, value)*
```

- 상태 인덱스는 정렬 후 **delta 인코딩 + varint**
- zstd 레벨 3 (속도/압축률 균형)
- `model_hash`로 스냅샷과 모델 불일치를 검출

### 8.3 용량 사전 경고

실행 전 예상 용량을 계산해 표시한다. 기본 경고 임계값 **200MB**, 거부 임계값 **사용 가능 메모리의 50%**.

경고 시 반드시 대안을 함께 제시한다: "`aggregate` 정책으로 전환하면 5MB", "`trackJoint`에서 `nStar3`를 빼면 1/1000".

## 9. 테스트 전략

### 9.1 교차 검증 (최우선, CI 필수)

동일 IR에 대해 DP와 MC(R=10^6)를 실행하고, **모든 셀이 MC의 95% 신뢰구간 안에 DP 값이 들어오는지** 검사한다. 셀의 5% 이상이 벗어나면 실패.

이것이 이 프로젝트의 가장 강력한 검증 수단이다. 최소 10개 모델(프리셋 포함)에 대해 CI에서 자동 실행한다.

### 9.2 해석적 정답 대조

닫힌 해가 있는 케이스는 절대 기준으로 사용한다.

| 케이스 | 정답 |
|---|---|
| 천장 없는 단일 엔티티 p, N회 | 이항분포 `B(N, p)` |
| 첫 당첨까지 시행 횟수 | 기하분포 |
| k번째 당첨까지 | 음이항분포 |
| 하드 천장 M회만 있는 경우 | 절단 기하분포 |

### 9.3 백엔드 일치성

- `ExactInt` 결과와 `ScaledF64` 결과를 비교. **상대 오차가 1e-10 이하**여야 한다 (§2.2 정밀도 주장의 실증)
- `ScaledF64`와 `F64`를 비교. 1e-300 이상 셀에서만 일치해야 하고, 그 미만에서 F64가 0이 되는 것을 확인
- **극소 확률 테스트**: `0.007^200 ≈ 1e-436` 상당의 셀에 대해 `ScaledF64`가 `ExactInt`와 유효숫자 10자리 이상 일치하는지 검증. **이 테스트는 D1 결정의 근거이므로 반드시 포함한다**

### 9.4 불변식 테스트

- 질량 보존 (§6.5)
- 포함관계: 모든 결과에서 `nPickup ≤ nStar3` (§3.5에 의해 정의상 참. 회귀 방지용)
- **지급 전파**: 200회 확정 픽업 지급이 있는 모델에서, `nStar3` 분포가 지급 없는 동일 모델 대비 **정확히 +1 이동**하는지 확인. 이중 계산(+2 이동)이나 미전파(+0)를 잡는다
- 지급 의미론: `consumesTrial`/`appliesTransitions` 4개 조합 각각에 대해 MC와 DP가 일치하는지
- 리프 확률 합 = 1 (모든 제어 상태에 대해)
- 리터럴 파싱: `"0.007"`이 정확히 `7/1000`인지 (f64 경유 시 실패해야 함)

### 9.5 골든 파일

각 게임 프리셋에 대해 기대 출력을 커밋하고 회귀를 감지한다. 프리셋 JSON 변경 시 골든 갱신을 명시적으로 요구한다.

### 9.6 퍼징

랜덤 IR 생성기로 컴파일러를 퍼징한다. 목표: 패닉 없음, 모든 잘못된 입력이 구조화된 에러 반환.

## 10. UI 계획 (`ui`)

### 10.1 블록 에디터

**Blockly**를 사용한다. 필요한 커스텀 블록 카테고리:

| 카테고리 | 블록 |
|---|---|
| 뽑기 결과 | 결과 정의(이름, 확률, 중첩 슬롯) |
| 상태 | 제어 변수 선언(초기값, **상한 필수**), 집계 변수 선언 |
| 확률 규칙 | 산술, 비교, if/else, 상태 참조, min/max/clamp |
| 전이 | `~가 나오면 → 상태 변경` |
| 트리거 | `시행 N회에 → 상태 변경` |
| 조건 | AND/OR/XOR/NOT, 카운터 비교 |

최상위 모델 컨테이너의 의미별 슬롯에 블록을 배치한다. 슬롯 내부 연결은 선언을
그룹화할 뿐 실행 순서를 뜻하지 않는다. Blockly 워크스페이스 → **Model IR JSON
직렬화**. JS 코드 생성 경로는 만들지 않는다.

## 12. 구현자 유의사항 (Codex 대상)

1. **`Fraction`/`Rational` 타입을 DP 내부 루프에 넣지 말 것.** 정확 모드는 §2.2(c)의 공통분모 BigInt 방식으로만 구현한다. GCD가 내부 루프에 등장하면 설계 위반이다.

2. **리터럴을 f64로 파싱하지 말 것.** `"0.007".parse::<f64>()` 후 유리수 변환은 금지. 십진 문자열 → 유리수 직접 파싱만 허용한다.

3. **엔진을 백엔드별로 복제하지 말 것.** `engine_mc`/`engine_dp`는 `Prob` trait에 대해 제네릭하게 한 벌만 작성한다.

4. **엔티티 카운트를 상태에 저장하지 말 것.** 저장은 리프 카운트뿐이고 엔티티 카운트는 파생값이다(§3.5). 확정 지급 시 리프 카운터만 증가시키면 상위 카운트는 자동으로 따라온다. 상위 카운트를 별도로 증가시키면 이중 계산이다.

5. **확률 표현식을 DP 내부 루프에서 평가하지 말 것.** §4.3의 사전계산 테이블을 반드시 거친다.

6. **MC 결과를 신뢰구간 없이 표시하지 말 것.** 모든 MC 출력 경로에 CI가 동반되어야 한다.

7. **`aggregate` 스냅샷이 기본값이다.** `full`은 명시적 확인 없이 실행되어서는 안 된다.

8. **프루닝 손실을 조용히 버리지 말 것.** 항상 누적하고 보고한다.

9. **성능 최적화는 §13.3 핵심 검증이 통과한 뒤, M8에서 진행할 것.** 정확성 검증(§9.1 포함)이 먼저다.
